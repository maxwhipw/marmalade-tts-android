Why split at all

The Engines tab lists everything in one scroll: the three on-device engines (Kitten, Kokoro, Pocket) as install cards, then the Cloud voices card last. Two reasons to draw a harder line between them:

It's a real boundary, not just tidiness

On-device voices send nothing anywhere. Cloud voices transmit your full text to a third-party provider per request — a genuine privacy line the app already spells out in a consent gate. A switch makes that line structural instead of "the card at the bottom".

There's only one cloud card today

A whole tab to reveal a single card can read as heavier than the thing it organizes. The cloud multi-provider system (Venice live-discovery, more providers to come) is what justifies it long-term — but right now the local side is where the 3 cards live.

All four mockups show the shipped A3 spec-column card with the new traffic-light speed meter (green Fastest / amber Fast / red Heavy). Counts on the switches are illustrative.

The seam

The cloud card sits in the same column as the on-device installs, so its very different contract (network, keys, your text leaves the phone) is easy to skim past. Every split below pulls it out.

T1

Segmented switch — top

A Material-3 segmented control directly under the title: On-device · Cloud. Selected segment uses the Toast chip colour, not accent orange (orange stays reserved for the Install/Configure CTA). The default lands on On-device. This is the direction most Android users already read as "two views of the same screen".

For

Compact, one row. Instantly familiar. The switch sits with the title so the whole list below is unambiguously "one side or the other". Scales cleanly if a third category ever appears.

Against

Pill segments compete a little with the top app bar for the same visual band. With one cloud card, the Cloud view can look sparse.

T2

Material tabs — top

Primary TabRow with the sliding underline indicator, sitting under the title like page-level sub-navigation. Same two destinations, but the affordance reads as "tabs of a section" rather than a toggle. This is the heavier, more permanent-feeling framing.

For

Unmistakably a navigation split; the underline animates between sides. Room for a count/badge per tab. Feels native to a top-level destination.

Against

Two horizontal bars stacked (app bar + tab bar) eat vertical space on a screen that's mostly cards. Tabs imply peers of equal weight — but On-device is the home base and Cloud is the exception, which a toggle expresses better.

T3

Segmented switch — bottom (thumb reach)

Same segmented control as T1, but pinned to the bottom of the content, floating just above the nav bar. The cards scroll; the switch stays under your thumb. Borrows the pattern from map/filter UIs where the toggle is a persistent bottom affordance.

For

Reachable one-handed on a tall phone without stretching to the top. Leaves the header clean. The switch stays visible while you scroll a long list.

Against

Two bars stacked at the bottom (switch + nav) can feel crowded and risk being read as part of the nav bar. Less conventional for a "which set am I viewing" control, which users expect near the top.

T4

Labelled sections — no tab (counter-option)

Keep the single scroll, but split it with two overline section headers — ON-DEVICE and CLOUD — with the privacy note riding the seam. No mode to toggle, nothing hidden; the boundary is drawn typographically. The honest answer to "is a tab overkill for one cloud card?"

For

Zero interaction cost — everything visible in one glance and one scroll. No empty-looking Cloud view. Trivial to build (two headers in the existing LazyColumn). The privacy note lands exactly where the boundary is crossed.

Against

Doesn't reduce the list's length or fully quarantine cloud — it's a softer line. If cloud grows to many provider cards, the single scroll gets long again and a real switch (T1) starts to earn its keep.

Recommendation

Lean T1 (segmented, top) — with T4 as the low-cost fallback

T1 is the strongest fit: a top segmented control reads instantly as "two views", keeps the header light (one row, not two bars like T2), and makes the on-device/cloud line structural — which matters because that line is a real privacy boundary, not just a category. Default to On-device; surface the "your text leaves the phone" note only on the Cloud side, where it belongs.

The honest caveat: today the Cloud view is a single card, so T1's Cloud tab can look sparse. If that bugs you on device, T4 (labelled sections, no tab) gets ~80% of the benefit for near-zero effort and no empty view — it just doesn't shorten the list. I'd ship T1 if we expect the cloud provider lineup to grow, T4 if cloud stays a single entry point for a while.

Rejected: T2 (Material tabs) — stacking a tab bar under the app bar spends too much vertical space and frames the two sides as equal peers when On-device is really home base. T3 (bottom switch) — clever for thumb reach but collides visually with the nav bar and isn't where users look for a "which set" control.

Scope if we build T1: a rememberSaveable tab-index state in EnginesScreen, split the LazyColumn content by local vs cloud, add a segmented control composable + two strings (engines_tab_local, engines_tab_cloud) across all 8 locales. Onboarding's engine picker is a separate screen and stays as-is. No engine/routing changes — purely presentational.

Nothing here is committed to the app yet — this is a decision surface. Say the word (and a variant letter) and I'll wire it into EnginesScreen.kt.
