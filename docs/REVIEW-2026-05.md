# Quality / pipeline / architecture review — 2026-05-25

Findings from a two-reviewer parallel audit + ExecuTorch feasibility research,
prompted by user-reported quality issues across all engines except Kitten Nano.

## The Kitten Nano paradox

Kitten Nano (smallest model, ~15M params, fp32 ONNX) sounds the **best** of all
five engines. Kitten Mini (80M, INT8-mixed) is slightly better in cadence but
audibly tinny. Kokoro v1.0 (fp32) is "wanting." Kokoro v1.1 English quality is
"very bad." Pocket TTS quality is the worst of the lineup.

Diagnosis: the smallest model isn't intrinsically the best — **the bigger
engines are losing handicap matches** to four compounding regressions:

1. **INT8 quantization noise** in flow-matching ODE solvers and audio decoders.
   Affects Pocket (all 5 graphs INT8), Kitten Mini (mixed-precision INT8).
2. **Silent sentence drops** in `SherpaEngine.kt:278` — `producer.trySend(...)`
   discards its result. When the channelFlow buffer fills (slower engines on
   long inputs), sentences are dropped while the native engine continues.
3. **Cancel-state race**: `Synthesizer.cancelled` is process-global, never
   re-armed mid-batch. Rapid Stop/Speak silently aborts the next playback.
4. **Streaming gate too tight**: a single emoji in the input forces the
   batched path, adding seconds of TTFA.

## Bugs found (ranked by severity)

### CRITICAL

- **C1 — Sherpa `trySend` silent sentence drops** (`SherpaEngine.kt:278-289`).
  Discarded `ChannelResult`; backpressure drops sentences. All four sherpa
  engines affected.
  Fix: replace with blocking `runBlocking { producer.send(...) }`.

- **C2 — Pocket `LSD_DECODE_STEPS = 1`** (`PocketEngine.kt:1487`). NekoSpeak
  ships 10 as default. With INT8 quantization noise riding the flow
  trajectory, 1 Euler step skips most of the trajectory.
  Fix: raise to 10 (user-tunable later).

- **C3 — Kitten Mini INT8-mixed bundle** (`KittenMiniEngine.kt:60-61`). Direct
  reproduction of the unblessed `kokoro-int8-v1.0` tinniness pattern
  documented in memory. Nano is fp32; Mini is INT8 → Mini sounds worse.
  Fix: ship `model.fp32.onnx` if upstream offers it; otherwise deprecate.

- **C4 — `Synthesizer.cancelled` process-global, never re-armed**
  (`Synthesizer.kt:153, 182, 312, 460, 501, 518, 589, 602`). Singleton-level
  `@Volatile Boolean`. Rapid Stop→Speak races the cancel flag against the
  new job; new job sees `cancelled=true`, aborts immediately, returns
  `Result.success` with no audio.
  Fix: per-job AtomicBoolean captured into the speak() coroutine scope.

- **C5 — `MarmaladeTtsService.onStop` no-op** (`MarmaladeTtsService.kt:422-427`).
  System TTS path can't cancel mid-synth. Screen readers / external apps
  experience the engine as unresponsive.
  Fix: hold a Job reference; cancel it from onStop.

- **C6 — `MarmaladeTtsService.onSynthesizeText` fully batched**
  (`MarmaladeTtsService.kt:388-411`). Runs full utterance through
  `runSynthesisPipeline`, then streams once. System-TTS callback API supports
  incremental `audioAvailable` — we throw away the streaming on the path
  most exposed to long inputs (whole-page reads).
  Fix: stream PCM chunk-by-chunk into the callback as it's produced.

- **C7 — Pocket all-graphs INT8 (the dominant Pocket defect)**
  (`PocketEngine.kt:203-207`). Including the most quantization-sensitive
  graphs: `flow_lm_flow_int8.onnx` (flow-matching network) and
  `mimi_decoder_int8.onnx` (audio synthesizer). NekoSpeak ships same files
  but compensates with LSD steps=10 + batch decoding.
  Fix: re-export from upstream PyTorch to fp32 or fp16 (see migration plan).

### HIGH

- **H1 — Sherpa engines lack mid-sentence cancellation**
  (`SherpaEngine.kt:258-261`). `generateWithCallback` inside `synchronized`
  block; callback only fires between sentences. 5-second sentence cannot
  be interrupted.
  Fix: use suspending Mutex (like PocketEngine), check coroutine cancellation
  in the callback path.

- **H2 — Streaming gate too tight on emojis** (`Synthesizer.kt:194-201`).
  `canStream = effect == NONE && hint.emotion == Neutral`. Single 🙂 in
  input → entire utterance goes through batched path → TTFA from ~400ms
  to several seconds.
  Fix: trivial-emotion predicate (allow streaming on Calm/low-intensity
  emotions), or apply gain-only prosody per-chunk.

- **H3 — Pocket `mimi_encoder` INT8 bakes quant error into voice cache**
  (`PocketEngine.kt:204, 829-861`). Voice embeddings cached to disk after
  going through INT8 encoder; quant error baked into voice identity for
  the lifetime of the install. Same for cloned voices.
  Fix: fp32 encoder + bump cache format version to invalidate prior caches.

- **H4 — Pocket ignores `speed`** (`PocketEngine.kt:382-384, 471-473`).
  Logs and drops the parameter. Cross-engine A/B testing with speed
  adjustments silently makes Pocket sound more different from sherpa engines.
  Fix: apply sox-style post-resample wrapper at engine layer.

- **H5 — `ProsodyApplier` cascades two linear-interp resamples**
  (`ProsodyApplier.kt:139-147`). No anti-aliasing. Double-pass through
  zero-order-hold-like interpolation noticeably degrades quality, especially
  on already-grainy engines (Pocket, Mini).
  Fix: sox-style pitch+tempo (WSOLA), or skip second resample.

- **H6 — `EffectChain.cave` in-place feedback** (`EffectChain.kt:94-100`).
  Inner loop reads `wet[i - delay]` after writing tap-1 into lower indices;
  tap-2 feeds on tap-1's wet output, tap-3 on tap-1+2. Effective feedback
  gain >1 on dense signal → `scaleAndClip` normalizes peaks → audible
  "ducking" of dry speech on CAVE preset.
  Fix: write taps to separate buffer, sum at end.

- **H7 — Kokoro `lengthScale` hardcoded to 1.0** (`KokoroV10Engine.kt:52`,
  `KokoroV11Engine.kt:49`). Sherpa multiplies by `speed` internally — fine —
  but Kokoro voices.bin metadata typically recommends ~1.1 for British
  voices. Currently British voices sound rushed.
  Fix: read length-scale from voice metadata, or expose as a knob.

### MEDIUM

- **M1 — Inconsistent thread budget across engines**: Kokoro=4, Kitten=2,
  Pocket=6. No rationale documented. On Tensor G3 (1×X3 + 4×A715 + 4×A510),
  threading spills onto A510 cores tank matmul perf.

- **M2 — Pre-roll heuristic uses only chunk 0's frames** (`PocketEngine.kt:497-516`).
  Edge case: short first chunk gives unrepresentative samples, K can over-
  or under-estimate. Mitigation: K capped at 3.

- **M3 — `EngineProfiles` runs English-centric rules on multi-lang Kokoro**.
  No language detection on the preprocessing stage.

- **M4 — `EngineProfiles` has two entries for "pocket"**
  (`EngineProfiles.kt:82, 97-103`). Dead duplication, cleanup only.

- **M5 — `MarmaladeTtsService.sampleRateFor` declares rate before
  `ensureModelLoaded`** (`MarmaladeTtsService.kt:579-586, 377`). Latent
  bug; all five engines currently 24 kHz so it's not yet broken.

### LOW

- **L1 — `playPcm` busy-waits with `Thread.sleep(10L)`** (`Synthesizer.kt:602-611`).
  Sub-100ms cancellation responsiveness ceiling.

- **L2 — Benchmark calls `engine.synthesizeStream` directly**
  (`BenchmarkViewModel.kt:194-205`). Bypasses Preprocessor; bench numbers
  don't reflect in-app audio.

- **L3 — `SherpaEngine` comments lie about model precision** (lines 60-63,
  326-329). Says "both engines currently ship `model.int8.onnx`" but
  Nano is fp32 now.

## Decision: ExecuTorch migration

Rather than fix engine-level bugs piecemeal on a stack that will eventually be
replaced, **direct migration to ExecuTorch + fp16 + KleidiAI** as the new
inference stack. Rationale:

- Existence proof: `react-native-executorch` already ships Kokoro-82M on-device
  via this exact stack.
- `org.pytorch:executorch-android:1.2.0` stable as of April 2026.
- AAR is **~11 MB** vs ORT's ~80 MB — net APK shrink expected.
- fp16 + KleidiAI enabled by default since v0.7. ARM Cortex-A715/A510 fast
  paths via i8mm + dot-product (no SME2 on Tensor G3, so no 3.9× win, but
  modest fp16 gains expected).
- Pocket's `stateful_module.py` already externalizes state — **exactly** the
  pattern ExecuTorch wants for streaming KV caches.
- Standard ops only: no custom kernels needed for Pocket / Kokoro / Kitten.
- Single inference stack across all engines → drops sherpa-onnx (recurring
  audio regressions) and onnxruntime-android.

### Migration phases

**Phase A — Pocket → ExecuTorch (priority 1)**
The hardest case, biggest quality complaint. If Pocket works end-to-end, the
sherpa engines are easier.

1. Stand up an ExecuTorch export pipeline (Python tooling). Load upstream
   `kyutai/pocket-tts` safetensors, `torch.export` each of the 5 graphs
   (text_conditioner, mimi_encoder, mimi_decoder, flow_lm_main, flow_lm_flow)
   to `.pte`.
2. Add `org.pytorch:executorch-android:1.2.0` AAR dependency.
3. Write `PocketEngineExecutorch` (parallel to current `PocketEngine`).
4. A/B test on device. If quality jumps to upstream-Python parity → kill
   old `PocketEngine`.

**Phase B — Kokoro v1.0 → ExecuTorch**
After Pocket is stable.

**Phase C — Kokoro v1.1 + Kitten Nano + Kitten Mini → ExecuTorch**

**Phase D — Remove sherpa-onnx + onnxruntime-android dependencies**
AAR shrink, single inference stack.

### Pipeline-layer bugs that survive the engine migration

These are independent of which inference runtime is used. They affect the audio
pipeline, system-TTS integration, and UX. To be addressed alongside or after
ExecuTorch migration:

- C4 (`Synthesizer.cancelled` race)
- C5 (`MarmaladeTtsService.onStop` no-op)
- C6 (`MarmaladeTtsService` non-streaming)
- H2 (streaming gate too tight)
- H5 (ProsodyApplier double resample)
- H6 (`EffectChain.cave` feedback)
- L1 (busy-wait)
- L2 (bench bypasses preprocessor)

### Engine-layer bugs that go away with ExecuTorch

The current engine implementations are replaced wholesale:

- C1 (Sherpa `trySend`) — drops with sherpa-onnx
- C2 (Pocket LSD steps) — moot when running PyTorch directly
- C3 (Kitten Mini INT8) — moot with fp16 ExecuTorch
- C7 (Pocket all-graphs INT8) — moot with fp16 ExecuTorch
- H1 (Sherpa cancellation) — drops with sherpa-onnx
- H3 (Pocket voice cache quant) — moot with fp16
- H4 (Pocket ignores speed) — re-implementable cleanly in new engine
- H7 (Kokoro lengthScale) — re-implementable cleanly in new engine
- M1, M3, M4 — refactored or moot in new engines
