Phase 0 — code all clear

Everything that had to be true in the source before a byte goes to Google. This phase is finished.

0.1espeak-ng compiled from source into the APKdone▸

Play's Device & Network Abuse policy forbids downloading executable code — dex, JAR, or .so — from outside Play. espeak-ng is now a pinned submodule built per-ABI into the APK, so nothing executable is fetched at runtime. This was the blocker for a year.

Consequence to state honestly in the listing: the distributed APK is GPL-3.0-or-later because espeak is compiled in. The source files stay MIT.
0.2targetSdk 36 — required by Play from ~31 Aug 2026done▸

Landed in d1a5c8e. AGP 8.7.3 → 8.9.3; Gradle untouched at 8.11.1. The two Android 16 behaviour changes that break most apps don't apply: the manifest sets no orientation or resizability locks, and MainActivity already called enableEdgeToEdge().

Verified on the Pixel 8a, which runs Android 16 — logcat confirms Background started FGS: Allowed … targetSdkVersion:36, so the foreground service still starts under the new target.

Still unverified: what edge-to-edge enforcement looks like. That needs your eyes, not a log line.

Phase 1 — signing yours

The one secret in the whole process. Google holds the app-signing key after enrolment; this is your upload key, and losing it means a support ticket, not a catastrophe — but back it up anyway.

1.1Generate the upload keystoreneeds you▸

Keep it out of the repo. Full walkthrough in docs/release/SIGNING.md.

keytool -genkeypair -v \
  -keystore ~/secure/marmalade-upload.jks \
  -alias marmalade-upload \
  -keyalg RSA -keysize 4096 -validity 10000
Back it up twice — KeePassXC entry plus an offline copy. This is the only artefact in the release that can't be regenerated.
1.2Wire keystore.properties (gitignored)I can do▸

Once the keystore exists, I write the four properties and confirm signingConfigs.release picks them up. Nothing secret is committed — app/build.gradle.kts already reads the file only if it's present.

2.5Foreground service declarations — the risky oneneeds you▸

Two types are declared, each needing a use-case justification and a demo video.

mediaPlayback — MarmaladeSynthService. Straightforward; a TTS engine playing audio is the textbook case.

specialUse — MarmaladeKeepaliveService. Weak fit, real rejection risk. It's user-opt-in, which helps. If it bounces, the fallback is cutting the keepalive service from the Play build rather than arguing.

Also declare REQUEST_IGNORE_BATTERY_OPTIMIZATIONS: defensible for a TTS engine whose core function is uninterrupted audio, and the prompt is user-initiated. Explain it in review notes.

Also worth knowing

5.1F-Droid, in parallel — not afterI can do▸

F-Droid review takes weeks, so it should be filed alongside Phase 2 rather than once Play is live. They build and sign from a tagged commit themselves, so no keystore is involved. The recipe pins gradle: [fdroid]. Expect a NonFreeNet anti-feature flag for the cloud API engine — that's a label, not a rejection.

5.2IzzyOnDroid — do not submitdecided▸

Their inclusion policy states they are "strongly opposed to apps which are fully or in part created by generative AI tools". This project's history is openly AI-assisted. Submitting means concealment or near-certain rejection, so the answer is neither. GitHub Releases + Obtainium fills that niche instead, and CI already attaches APKs on tag.

5.3The two flavors, revisitedopen▸

play and fdroid now differ in exactly one thing: F-Droid shows a GitHub Sponsors link in About and Play doesn't. You've noted that unsettled policy isn't the same as forbidden, which is fair — the omission is caution, not a rule. Leaving it out for now; collapsing to one flavor is a small change whenever you want it.
